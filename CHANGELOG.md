# Changelog

All notable changes to this plugin are listed here. Versions follow [Semantic Versioning](https://semver.org/). The DeepSeek Harness versions a release runs on are in `engines.dsh` in `package.json`.

## Unreleased

- Two Matriarc switches per coordinator, in the setup step and on the Coordinator page: the coordinator chat (off by default) and new Executor Sessions (on by default). Whalepod runs `/matriarc on` or `/matriarc off` in the session; without the Matriarc plugin the switches do nothing.

## 0.5.0 - 2026-11-15

### Added

- New coordinator opens a setup step before anything is created. It shows the name, the model for the coordinator and the model for its Executor Sessions, already filled in. Nothing exists until you press Create, and the chat opens only then. Choose folder... and Type a path open the same step for the folder you gave.
- The name field shows a suggested name from the built-in list in grey. Leave the field empty and the coordinator gets exactly that name. If another coordinator took the name in the meantime, it gets another free one. A name you type is checked like a rename, as before.
- The two model pickers start on DeepSeek V4.1 Flash when DeepSeek Harness offers it: reasoning effort Low for the coordinator and High for its Executor Sessions. When several providers offer the model, the provider of your default model is used. You can change both in the setup step, with the same pickers as on the page, or later on the page. Nothing is set before you press Create.
- A picker starts empty ("Not set" for the coordinator, "Same as coordinator" for the Executor Sessions) when the model is not available, when the model does not offer the effort meant for that picker, or when the models of your default model's provider could not be loaded. No other effort and no other provider is taken in its place.
- Your first coordinator goes through the same setup step: with no coordinator yet, the page offers New coordinator.
- Create waits until the setup step has loaded its suggestions. If they cannot be loaded, the step says so; a coordinator you create then gets an automatic name and no model settings.
- A model, name or folder that is refused creates nothing. The setup step stays open and shows the reason next to its fields.
- Once a coordinator is created the setup step closes, also when its chat could not be opened. A notice says so, and the coordinator is in the list with its Open chat button.
- The model pickers, in the setup step and on the page, name the provider of each model, so the closed picker shows which provider the chosen model comes from.

### Changed

- New coordinator followed by Enter still creates a coordinator with the suggested name, now with the models the setup step shows. In earlier releases a new coordinator had no model settings: its chat started on the DeepSeek Harness default and its Executor Sessions on the chat's model. Choose "Not set" and "Same as coordinator" in the setup step to get that again.
- Coordinators you already have keep their model settings, also when they have none. A coordinator that comes about without the setup step gets no model settings: a new session you start in a coordinator's sidebar group keeps the model you started it on.
- What was checked: the test suite on a fake host, and the model ids in the dsh 0.2.2-rc.3 sources and in a running dsh 0.2.2-rc.3. In the desktop app (dsh-desktop 0.2.2-rc.3) with a real model: nothing was created while the setup step was open, Create without typing gave the suggested name with DeepSeek V4.1 Flash at Low in the chat and at High in a new Executor Session, a typed name and "Same as coordinator" showed on the page after Create, a duplicate name was refused in the step, Esc and Cancel created nothing, and Type a path kept the name and the picks. Not run in the app: Choose folder... with the system's folder picker, a picker that starts empty, suggestions that cannot be loaded, the first coordinator, and a chat that cannot be opened.

## 0.4.1 - 2026-11-15

### Fixed

- A coordinator could not use your skills. Asked to look into one, it answered "the coordinator may not access the dsh home". There were two causes, and both date from 0.1.0. The plugin refused coordinators and Executor Sessions every file in the DeepSeek Harness home folder (`~/.dsh`), where your skills are. And a coordinator did not have the `skill` tool, so DeepSeek Harness did not show it the list of skills either. A coordinator now has the `skill` tool: it sees the same skills as any session, loads one, reads the files next to it, and names the skill in the Assignment, so that the Executor Session uses it. A coordinator still does not carry out a skill itself.
- Executor Sessions and their Teammates could load a skill, but the plugin refused them the files and scripts next to it, every shell command that named `$DSH_HOME` or `~/.dsh`, the office outputs DeepSeek Harness writes to its home folder, and a project's own `.dsh/skills` folder. All of these work now.
- The check that keeps coordinators and Executor Sessions out of the plugin's own state folder had gaps, found in a review of this release before it shipped. Most came with the narrower check of this release. Two are older, from 0.1.0, where a broader rule had covered them: a call with very many arguments, and a path of the form `~/link/..`. All are fixed here together.
  - Another name of the same folder was not recognised: on macOS the alias `/System/Volumes/Data/...` and the `/.vol/...` form, on a volume that ignores letter case a different case, and a hard link to the state file. The check now compares what a path leads to (device and inode) and not only how it is spelled.
  - A call with more than 500 text arguments was checked only up to the 500th. Every argument is read now. A call beyond what the check reads (100 000 texts, 2 000 paths, 64 levels of nesting) is refused with a text that says to split it; no call a model writes comes near these limits.
  - `~/link/../...`, where `link` is a symlink, was resolved differently from how the file is opened. So was a path with a leading blank.
  - A search without a path was not checked against the session's working directory, which an Executor Session can change. Such a search is now refused when the working directory is above the state folder, and changing the working directory into the folder is refused. Where a search starts is read only from its `path`: nothing else in the call, such as an `include` filter or an extra argument that names a folder, stands in for it.
  - A path that starts with `file://` was checked without that prefix, while the file tools open it with it, as a folder named `file:`. A search path that starts with `~` was checked as your home folder only, while the search tools read it as a folder named `~`. Every such reading of a path is checked now.
  - `apply_patch` names its files inside the patch text, where only the text check looked. Those paths now get the full path check.
  - The text check for shell commands ignored other letter cases. It does not any more.
  - For dsh's file and search tools a path with a NUL character is refused, and so is a path on one line that is longer than any operating system opens. Other tools, such as MCP tools, are not refused for long text under a key like `input`. A long spelling of a short path, such as `/././...` repeated, is checked like the short path.
  - A call with very long arguments could keep the host busy for seconds while it was checked, which was so since 0.1.0. The check now takes milliseconds for such a call: about 30 ms for a text of 2 MB, whatever it holds. The path lookups of one call are bounded as well (2 000 paths, 4 000 readings of them), and a call at these limits takes 1 to 2.5 s when its paths are plain or their parts do not exist. A path with `..` through a deep tree of existing folders costs up to about half a second each, so a call with many of them can keep the host busy for longer. Building such a tree needs an Executor Session's shell, which can keep the machine busy in other ways anyway (`docs/security.md`, Known limits 23).
- Also fixed (present since 0.1.0):
  - `coordinatorExtraTools` accepted some of DeepSeek Harness's own tools that a coordinator must never have: `run_code`, `str_replace_editor`, `subagent_oar`, `ralph`, `load_workspace_dependencies`, the browser tools (`stagehand_*`) and four tools that read session logs (`session_trace`, `session_event_read`, `session_event_search`, `session_event_trace`). They are refused now, like `bash` and `session_search`. No coordinator had one of them unless you had added it by name.
  - `executor_start` could keep the host busy for about a second when the Assignment was nearly all line breaks, or named a working directory tens of thousands of characters long. It answers at once now, and a folder path of more than 1000 characters is refused.
  - An Assignment reached its Executor Session exactly as the coordinator wrote it, also when it held text that looks like one of the plugin's own blocks, such as a copy of the Executor prompt block. Such a tag is now replaced with `[removed tag]`, as in a coordinator's later messages. The rest of the Assignment is unchanged.
- A coordinator takes a loaded skill as instructions. A skill in the skills folder of the coordinator's own project (`.dsh/skills` or `.agents/skills`) may have been written by an Executor Session. When such a folder exists, the Assignments a coordinator writes after loading a skill in the same turn are now recorded as a notice from the coordinator and not as your instruction, as after any other text from an Executor Session. The coordinator is told which folder caused this. Your own skills in the DeepSeek Harness home folder are trusted as before. The list of skills that DeepSeek Harness shows a coordinator is not covered by this; docs/security.md (T1 and T3) says what that means.

### Changed

- The plugin no longer keeps coordinators and Executor Sessions out of the DeepSeek Harness home folder as a whole. There they are now treated like every other session of yours: DeepSeek Harness's own sandbox and Auto review decide, not the plugin. In practice they can read files there, the credentials file, the profiles and the session logs included, as any session can. Writes there need your approval in Ask me mode, and in Auto review the reviewer decides about each one. Up to 0.4.0 the plugin refused such calls itself: reliably for the file tools, and for shell commands only in the spellings it recognised. docs/security.md (T10, T12 and Known limits 3 and 5) lists what now rests on DeepSeek Harness alone, and docs/decisions.md (decision 70) has the reasons.
- The plugin still closes its own state folder (`storages/dsh-coordinator` in that home folder) to coordinators, Executor Sessions and Teammates, for reading and for writing. It holds each coordinator's Executor prompt, memory and model settings, which change only on the Coordinator page and through the memory tools. For the file and search tools this is enforced whatever name of the folder a call uses. For a shell command of an Executor Session the plugin can only refuse the spellings it recognises, as before; there DeepSeek Harness's sandbox and Auto review are the control. A refused call now names this folder only, and a search that starts above it is told to search a narrower folder. Such a search no longer counts towards the notice a coordinator gets when an Executor Session tries three times to reach the folder. Such a search, for example one at your home folder or at `~/.dsh`, is refused as in earlier releases; a search in a project, in `~/.dsh/skills` or in any other folder that does not contain the state folder works.
- In Ask me mode the plugin no longer refuses file tools that write to the system temp folders. DeepSeek Harness's sandbox allows those folders to every session, and a shell command in the same session could always write there.
- A coordinator can open session logs as files, which the plugin refused before. They hold the unfiltered text of Executor Sessions and of other coordinators' chats. The `session_search` tool stays off a coordinator's tool list.
- What was checked: the test suite on a fake host, and the dsh 0.2.2-rc.3 sources for how an ordinary session reaches the home folder and loads skills. In the desktop app (dsh-desktop 0.2.2-rc.3) with a real model, before the fixes to the state-folder check: a coordinator listed the user's skills and loaded one with `skill`, an Executor Session loaded the same skill and reported back, and a coordinator's read of the plugin's state file was refused with the new text; the list and the refusal were seen again in the app run for 0.5.0. Not run in the app: a read of a file next to a `SKILL.md`, a skill's script in an Executor Session, the state-folder fixes, and everything else in this entry. The state-folder fixes were tested in the test suite and with probes on a real file tree on macOS, with the spellings from the reviews and from the final audit, and for two search cases with the ripgrep that DeepSeek Harness ships.

## 0.4.0 - 2026-11-15

### Added

- You can choose a model per coordinator on the Coordinator page: one for the coordinator and a separate one for its Executor Sessions. Two rows under the folder, "Coordinator model" and "Executor model", list the models DeepSeek Harness offers, grouped by provider, with the reasoning effort next to the model as in the chat's message box. A change saves at once.
- "Coordinator model" is the model the coordinator's chat runs on, from its next reply on. It is one setting with the model picker in the chat: a change in either place shows in both. A chat that is reopened starts on it.
- "Executor model" is the model new Executor Sessions of that coordinator start on, and their Teammates with them. Its first choice, "Same as coordinator", is the default and what earlier releases did. It applies to Executor Sessions started from then on. Running ones keep their model, and a model you change by hand in an Executor Session's own chat stays in that session.
- A model that is no longer available, for example after you signed out of its provider, stays selected with a note on the page. New Executor Sessions then start on the coordinator's model, or on the DeepSeek Harness default, and the coordinator is told when it starts one. The model is used again once it is available again.
- When DeepSeek Harness cannot say whether the Executor model is available, because its provider's model list fails at that moment, no Executor Session is started on another model in its place: the coordinator is told to try again, and the page says that the model could not be checked.
- The "Coordinator model" row says so when the chat runs on another model than the one shown, for example after you restored an archived chat in DeepSeek Harness instead of using Reopen. The page can tell only for a chat that is loaded.
- Choosing a model on the page does not change the model your other sessions in DeepSeek Harness start on. Choosing one in a chat's model picker still does, because DeepSeek Harness saves that choice as its default.
- Only you change the two settings. No tool of a coordinator or an Executor Session reads or sets them, and the host accepts only models and reasoning efforts that DeepSeek Harness lists, checked on every change on the page, on every change in the coordinator's chat, and again each time a setting is used for a new session.
- Existing coordinators need nothing: without a setting they behave as before, and the state file keeps its format. For the same reason an earlier release still reads the file, and its first save drops the model settings without a notice. Keep a copy of `state.json` before you go back to one (README, Upgrading from an earlier release).
- What was checked: the test suite on a fake host, and the dsh 0.2.2-rc.3 sources for the model APIs the feature uses. In the desktop app (dsh-desktop 0.2.2-rc.3) with a real model: the two rows list the models with their reasoning effort, a model set on the page showed in the coordinator's chat and ran there, a new Executor Session started on it, and the model that other new sessions start on did not change. A separate Executor model was run there only with the settings a new coordinator gets in 0.5.0: the Executor Session started on its own reasoning effort. Not run in the app: a change in the chat's model picker showing on the page, a model that is no longer available, and the list following a provider you set up or sign out of while the page is open.

## 0.2.1 - 2026-11-15

### Fixed

- A notice from an Executor Session that arrived while its coordinator was working showed up in the queue above the coordinator chat's message box, as if you had queued a message yourself, with the buttons to edit, delete and send it. The plugin no longer queues its notices in a coordinator's chat. A notice that would wake a coordinator now waits inside the plugin until the coordinator's turn has ended and then opens the next turn; several waiting notices open one turn together, in the order they arrived. A message you type meanwhile still runs first and keeps your authority. The fault was present since 0.1.0.
- After a turn you stopped, or one that failed, the waiting notices stay in the plugin and start nothing. A notice made just before that moment that had not gone out yet waits with them, so a result reported a moment before you press Stop does not start the coordinator again a moment after. Your next request runs without them and keeps your authority. They open a turn of their own once a turn of the chat has ended normally, or they go out together with the next notice that wakes the coordinator. Two exceptions: when the chat is archived and reopened, and when the plugin is reloaded or the app is restarted, these notices are added to the chat as background, and the first request you type there then counts as one that follows a notice. A reload or restart while the coordinator's chat is not loaded in DeepSeek Harness drops them, with a line in the log. Until then the coordinator has not read them; the Coordinator page and the pane show each Executor Session's state as before. While a message or steering of yours is still parked in the chat after a Stop, the plugin starts no turn there and no look-in is collected.
- Messages the plugin sends into an idle Executor Session (coordinator messages, messages between Executor Sessions, the note after Resume) now start its turn directly instead of going through that session's queue, and the tool results of `executor_message` and `executor_send` say "started" for it. Two known limits remain there. A message that reaches an Executor Session in the moment its turn is being stopped shows in that session's queue until the stop has settled, as before. A message to an idle Executor Session in which you have parked a message of your own starts a turn that takes your first parked message with it.
- Notices kept for a coordinator whose chat is archived are bounded at 200 instead of 50, the same bound as for waiting notices, so none is cut when waiting notices join them. When the bound is passed, the log says how many were dropped. A delivery that fails puts its notices back and is tried again.
- What was checked: the dsh 0.2.2-rc.3 sources, and a run in `dsh web` rc.3 with a scripted model (a result for an idle and for a busy coordinator, two results at once, a message typed meanwhile, messages to idle Executor Sessions). In the desktop app (dsh-desktop 0.2.2-rc.3) with a real model: a Report that arrived while the coordinator was working put nothing in the queue and opened a turn when the running one ended, and a message typed while it was working was the only entry in the queue and ran next. The behaviour after Stop, the parked-input rule, the retry and the bound are covered by the test suite on a fake host only. Not run: the two limits above, a restart while notices wait, and the folder card after a notice turn.

## 0.2.0 - 2026-11-15

### Added

- Each coordinator has a memory: one short page of notes that it shares with its Executor Sessions, with what a fresh coordinator or a new Executor Session would otherwise have to ask you again, such as your standing preferences and rules, decisions, how you like a kind of work done, split and reported, and lasting facts about your projects. The coordinator and the Leads of its Executor Sessions read it with `memory_read` and rewrite it with `memory_update`, by themselves and in the turn they learn something; the coordinator also saves or drops something when you tell it to remember or forget it. The page survives compaction and restarts. The coordinator has it in its context; an Executor Session starts without it, gets the parts that matter in its Assignment and can read the whole page; Teammates have no access. Every write replaces the whole page and names the revision it is based on: when the page changed meanwhile, nothing is saved and the writer merges and sends again. You can read and edit the memory in the Memory row on the Coordinator page, which also shows who changed it last (you, the coordinator or an Executor Session) and which Executor Sessions changed it since you last saved it there (for your information; "Mark as reviewed" or a Save of your own edit clears that list). The row follows the memory on its own: a change by the coordinator or an Executor Session simply shows, with nothing for you to apply or save. It keeps your draft when the memory changes while you have unsaved edits, and has a "Use memory" switch per coordinator: off, the coordinator and its Executor Sessions get no notes and cannot change them, and the text is kept. The page is meant to stay short; 6000 characters are a safety bound. The coordinator also holds its Executor Sessions to the memory: when a Report or a notice shows one working against a rule or preference in it, the coordinator reminds it how you want it done, stops it when needed, and tells you. The memory never counts as your instruction: it cannot allow a folder or answer an approval, and no host check accepts it in place of your own words. What you type in an Executor Session wins there over the memory and the Executor prompt; what you say in the coordinator's chat wins over the memory. When an Executor Session changes the memory while the coordinator works on your request, or the coordinator reads a memory that Executor Sessions changed since you last saved it, the Assignments written in the rest of that turn are recorded as the coordinator's notice and not as your instruction. It is written by models, Executor Sessions included, and can still shape the Assignments the coordinator writes for you, so review it on the Coordinator page from time to time, or switch it off for unattended work on untrusted content (see `docs/security.md`, T3 and T11a). Each writer can change a memory at most 10 times within 10 minutes, and all Executor Sessions of a coordinator together at most 30 times. Text in the memory that looks like one of the plugin's or dsh's block tags is replaced with `[removed tag]`. The memory is stored in the plugin's state file, whose format is unchanged, so 0.1.1 still reads the file and its first save drops the memory without a notice. Keep a copy of `state.json` before you go back to 0.1.1 (README, Upgrading from an earlier release).
- Look-ins: while an Executor Session works, its coordinator can now look in on it at times it picks itself with its new `executor_check_later` tool, when the memory has rules for that work. A look-in shows short previews of what the Executor Session wrote (its latest message, its last Reports and its todo list); when the work goes against a rule, the coordinator reminds it how you want it done and tells you in one line, and otherwise ends quietly and looks again later, further apart each time. Executor Sessions now keep a todo list and send a short progress Report when they make a decision that shapes the work; neither wakes the coordinator. Two new settings in "Notices to coordinators": the shortest gap of a look-in (`checkLaterMinMinutes`, 5 minutes, at most 240) and the look-ins one executor may get until you write again, in the coordinator's chat or in the executor (`checkLaterMaxPerExecutor`, 6). Look-ins do not count toward the wake limit. A pending look-in is not kept across a plugin reload or an app restart. At most 20 progress Reports per executor within 10 minutes reach the coordinator as notices; further ones are recorded and shown at the next look-in.
- What was checked: the test suite on a fake host. In `dsh web` 0.2.2-rc.3 with a scripted model: a memory change by the coordinator and one by an Executor Session showed in the Memory row without Save, and "Mark as reviewed" cleared the list. In the desktop app (dsh-desktop 0.2.2-rc.3) with a real model: a coordinator wrote its memory, and the row showed the new text and "Last changed by the coordinator" without Save. Look-ins are covered by the test suite only; also not run with a real model: a memory change by an Executor Session, your own edit and Save in the row, and the "Use memory" switch.

## 0.1.0 - 2026-11-13

First public release of Whalepod (package `dsh-whalepod`), for DeepSeek Harness 0.2.2-rc.2 and later 0.2.x releases.

### Coordinators

- A coordinator is a chat whose agent delegates work. It hands each task to its own Executor Session, follows it and reports the results.
- Up to 20 coordinators can be live at once. Each has a name from a built-in list (for example "Noether" or "李白"), its own folder next to dsh's default workspace and its own sidebar Workspace. The name and the folder for new work can be changed on the Coordinator page.
- A new session started in a coordinator's sidebar group becomes another coordinator with the first message the user types in it.
- Each coordinator has an Executor prompt: standing instructions that every Executor Session it starts receives. Only the user can change it.
- Coordinators have the `executor_*` tools plus tools to read and search files, ask the user and keep a todo list. They have no shell, write, web or browser tools, and the host refuses calls outside that list. `coordinatorExtraTools` can add tools of other plugins that do not execute, write or spawn work.
- Archive coordinator archives the chat and its finished Executor Sessions without deleting files, and can also remove the coordinator's sidebar group. Reopen brings an archived coordinator back with a new chat. Delete coordinator removes an archived coordinator's entry from the page; its sessions, folders and files stay.
- When a coordinator chat is deleted from the sidebar, the coordinator keeps its Executor Sessions and the page shows the chat's state. Reopen chat or Start chat creates a new chat that receives what waited.

### Executor Sessions

- Each Executor Session is an ordinary dsh session with its own Lead and folder, on the user's Standard preset, with Agent Teams enabled. The executor shows as running while any Teammate works, and the coordinator hears once when the whole team is done.
- Executor Sessions run in dsh's Auto review by default. The Coordinator page switches new ones to Ask me (`workspace-write`). The plugin never picks a looser preset.
- Executor Sessions of the same coordinator can message each other (`executor_peers`, `executor_send`). Executor Sessions of different coordinators cannot.
- Each Executor Session gets its own sidebar group at its folder, titled "<coordinator name> · <folder name>" and placed after its coordinator's group. An executor in a folder that is already one of the user's Workspaces joins that Workspace.
- An Executor Session starts with the working title its coordinator gave it. With dsh's session-titles generator enabled, dsh retitles it from its Assignment and later from what the user types; a generated title that looks like a coordinator's is not taken over.
- Leads send Reports with `coordinator_report`. Notices reach the coordinator in batches, as fenced data, and a result reaches the coordinator once.
- Up to 128 Executor Sessions run at once across all coordinators (`maxRunningThreads`); further starts queue.
- Loop brakes pause an executor until the user resumes it: one that wakes its coordinator too often (60 times in 10 minutes by default), and executors that message each other past the pair limit (40) or the sender limit (200) in 10 minutes. A daily turn budget (`threadTurnBudget`) is off by default; set one for unattended use.

### Pages and settings

- The Coordinator page lists the coordinators and, for the selected one, its folder, its Executor prompt and its Executor Sessions grouped as Needs you, Running, Standing by and Finished. Archived Executor Sessions are listed read-only in a collapsed Archived group.
- The Executor Sessions pane in the right sidebar lists a coordinator's executors next to its chat, and the sibling executors next to an executor.
- Approvals, questions and folder confirmations of executors appear on their rows and in the coordinator chat.
- Plugins > Whalepod shows a short introduction and a settings form for the running cap, the daily turn budget, the loop brakes, notice timing and the defaults for new coordinators. Changes apply without restarting the plugin and are saved in the profile's patch. A value a setting refuses reads as its default and never stops the plugin from loading.
- The interface is available in English and Chinese. The README is available in English, Chinese and German.

### Security

- Folders outside a coordinator's own folder, and existing folders below it, need the path typed by the user in that coordinator's chat and then the user's confirmation. The home folder, dot folders, system folders and the dsh home are always refused.
- Executor Sessions, their Teammates and the coordinators cannot read or write the dsh home (credentials, session logs, plugin state). The host enforces this.
- An Assignment counts as the user's instruction only when the user asked for the work.
- The state file is checked against the Session logs it names before it is used, and fails closed.
- [docs/security.md](https://github.com/simveit/dsh-whalepod/blob/main/docs/security.md) has the threat model and the known limits.

### Upgrading from pre-release builds

- The package was called `dsh-coordinator`. Remove it and add `dsh-whalepod` (README, Upgrading from an earlier release). Coordinators, Executor Sessions, the plugin state and settings are kept, because the plugin id, the state folder and the log marks keep the old name. A settings row in the profile patch whose `name` is `dsh-coordinator` must be changed to `dsh-whalepod`, or dsh skips it.
- A version 1 state file is migrated to version 2, and a copy is kept once as `state.v1.json`. The migrated coordinator gets a name and starts new Executor Sessions in its folder next to dsh's default workspace; existing Executor Sessions keep their folders.
- Sessions on the old `thread` and `coordinator` presets are moved to Standard.
- The tools were renamed from `thread_*` to `executor_*`. The old parameter names `thread` and `brief` still work.
